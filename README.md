# PayFlow API

A simplified wallet/money-transfer REST API, built with Spring Boot, Spring Data JPA,
and an in-memory H2 database. It lets a client register users, look them up, and
record money transfers between them — no UI, just the backend a frontend team
could plug into.

## Running it

Requirements: JDK 17+ and Maven (or just the included Maven wrapper if present).

```bash
mvn clean package
java -jar target/payflow-api-0.0.1-SNAPSHOT.jar
```

or, for local development:

```bash
mvn spring-boot:run
```

The app starts on `http://localhost:8080`. The H2 console is available at
`http://localhost:8080/h2-console` — use JDBC URL `jdbc:h2:mem:payflow`,
user `sa`, empty password.

## What each layer does

```
src/main/java/com/payflow/api/
  PayflowApiApplication.java   – application entry point (@SpringBootApplication)
  entity/                      – JPA entities: User, Transaction
  repository/                  – Spring Data JPA repositories
  service/                      – application/business logic, injected into controllers
  controller/                  – REST controllers that expose HTTP endpoints
```

- **entity** — plain Java classes annotated with `@Entity`. Each one maps directly
  to a database table; Hibernate generates the schema from these classes at
  startup, so there is no hand-written SQL for table creation.
- **repository** — interfaces extending `JpaRepository`. Spring Data JPA generates
  the implementation at runtime (CRUD methods, plus the custom query methods
  declared here), so there is no DAO boilerplate to write.
- **service** — holds the business logic and is the only layer the controllers
  talk to. It depends on repositories through constructor injection.
- **controller** — `@RestController` classes that map HTTP routes to service
  calls and handle request/response JSON conversion.

## Spring Boot's three features, as they show up in PayFlow

1. **Embedded server** — there is no separate Tomcat installation or WAR file to
   deploy. `spring-boot-starter-web` bundles an embedded Tomcat, so
   `java -jar payflow-api-0.0.1-SNAPSHOT.jar` brings up a listening HTTP server on
   port 8080 by itself.
2. **Auto-configuration** — adding `spring-boot-starter-data-jpa` and the H2
   dependency is enough for Spring Boot to auto-configure a `DataSource`, an
   `EntityManagerFactory`, and a `TransactionManager` with no manual XML or Java
   config. `application.properties` only tweaks the defaults (DB URL, showing SQL,
   enabling the H2 console).
3. **Production-ready defaults** — `spring.jpa.hibernate.ddl-auto=update` and
   `spring.jpa.show-sql=true` are one-line overrides of sensible defaults Spring
   Boot already ships with; the app also exposes actuator-style conventions (e.g.
   predictable error responses) without any extra setup.

## Entities

### User

| Field | Java Type | DB Column | Notes |
|---|---|---|---|
| userId | Long | user_id | Primary key, auto-generated. Never in the POST body. |
| name | String | name | Full name, e.g. "Priya Sharma" |
| upiId | String | upi_id | e.g. "priya@okaxis" — must be unique |
| balance | Double | balance | Opening wallet balance in INR, e.g. 5000.0 |
| phoneNumber | String | phone_number | 10-digit mobile number |

### Transaction

| Field | Java Type | DB Column | Notes |
|---|---|---|---|
| transactionId | Long | transaction_id | Primary key, auto-generated. |
| senderUpiId | String | sender_upi_id | UPI ID of the person sending money |
| receiverUpiId | String | receiver_upi_id | UPI ID of the person receiving money |
| amount | Double | amount | Amount transferred in INR |
| note | String | note | Optional note, e.g. "dinner split" |

camelCase Java field names (`upiId`, `phoneNumber`) automatically become
snake_case column names (`upi_id`, `phone_number`) — this is Hibernate's default
physical naming strategy mapping Java identifiers to SQL identifiers.

## Repository layer

```java
public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByUpiId(String upiId);

    @Query("SELECT u FROM User u WHERE u.balance > :amount")
    List<User> findUsersWithBalanceAbove(@Param("amount") Double amount);
}
```

### SQL generated for `findByUpiId`

```sql
select
    u1_0.user_id,
    u1_0.balance,
    u1_0.name,
    u1_0.phone_number,
    u1_0.upi_id
from
    user u1_0
where
    u1_0.upi_id=?
```

(a) **How JPA derives it from the method name** — Spring Data JPA parses the
method name `findByUpiId` into a subject (`find`) and a predicate (`By UpiId`).
It matches `UpiId` against the `upiId` property on the `User` entity and builds
a JPQL query equivalent to `SELECT u FROM User u WHERE u.upiId = ?1`, which
Hibernate then translates into the SQL above. No method body is needed — the
name alone is the query specification.

(b) **What the `?` placeholder means** — it is a positional JDBC parameter.
Instead of concatenating the `upiId` argument into the SQL string, the driver
sends the query text and the parameter value separately; the database binds the
value when it executes the prepared statement. This is what prevents SQL
injection and lets the database cache/reuse the query plan across calls with
different values.

## Service layer

`UserService` and `TransactionService` are both `@Service` beans that depend on
their respective repositories via constructor injection with `@Autowired`. See
the comment above each constructor in the source for what Spring does at
startup to wire this automatically:

```java
// At startup, Spring's component scan finds this class (@Service) and the
// UserRepository interface (a Spring Data JPA repository). It generates a
// proxy implementation of UserRepository and registers both as beans in the
// application context. @Autowired then asks the container for a bean that
// satisfies the UserRepository type, and the container injects that proxy
// here via constructor injection - no manual "new UserRepository()" needed.
```

## REST endpoints

| Method | Endpoint | What it does |
|---|---|---|
| POST | `/users` | Register a new user. Accepts JSON body with `@RequestBody`. Returns the saved User object (with the generated `userId`). |
| GET | `/users` | Returns all registered users as a JSON array. |
| GET | `/users/{id}` | Returns a single user by `userId` using `@PathVariable`. |
| GET | `/users/upi/{upiId}` | Returns the user matching that UPI ID (uses `findByUpiId`). |
| GET | `/users/balance-above/{amount}` | Returns users whose balance is above `amount` (uses the `@Query` JPQL method). |
| POST | `/transactions` | Records a money transfer. Accepts `senderUpiId`, `receiverUpiId`, `amount`, `note` in the JSON body. Returns the saved Transaction. |

### `@RequestBody` demonstration

`UserController` has two POST handlers: `createUser` (with `@RequestBody`) and
`createUserWithoutRequestBody` (same shape, no `@RequestBody`), both logging the
incoming User's fields with `System.out.println` before returning it.

With `@RequestBody`:

```bash
curl -s -X POST http://localhost:8080/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Priya Sharma","upiId":"priya@okaxis","balance":5000.0,"phoneNumber":"9876543210"}'
```
Console output:
```
createUser (with @RequestBody) received: Priya Sharma, priya@okaxis, 5000.0
```

Without `@RequestBody`, same JSON body:

```bash
curl -s -X POST http://localhost:8080/users/no-request-body-demo \
  -H "Content-Type: application/json" \
  -d '{"name":"Test2","upiId":"test2@ok","balance":200.0,"phoneNumber":"8888888888"}'
```
Response:
```json
{"userId":null,"name":null,"upiId":null,"balance":null,"phoneNumber":null}
```
Console output:
```
createUser (without @RequestBody) received: null, null, null
```

**Why the fields are null without `@RequestBody`:** Spring MVC only reads and
deserializes the raw HTTP request body into a method parameter when that
parameter is explicitly annotated with `@RequestBody` — that annotation is what
tells the `HttpMessageConverter` machinery (Jackson, for JSON) to parse the body
against the parameter's type. Without it, Spring instead tries to populate the
object using its data-binding mechanism for request parameters (query string or
form fields), which here finds nothing matching, so it constructs the `User`
with its no-arg constructor and leaves every field at its default (`null` for
objects, `0`/`0.0` for primitives). The JSON payload is never touched, so the
object comes back empty.

## Custom queries: three approaches, compared

1. **Derived query methods** (`findByUpiId(String upiId)`) — Spring Data parses
   the method name and builds the query automatically. Fastest to write, but
   limited to what the naming convention can express, and the method name gets
   unwieldy for complex conditions.
2. **`@Query` with JPQL** (`findUsersWithBalanceAbove`) — you write the query
   against entity names and properties (`User`, `u.balance`), not table/column
   names. It's portable across databases (Hibernate translates it) and lets you
   express joins, aggregations, and conditions a derived name can't.
3. **Native SQL** (`@Query(nativeQuery = true)`) — you write raw SQL against the
   actual table/column names. Most flexible and can use database-specific
   features, but it's the least preferred for day-to-day use because it breaks
   database portability (SQL dialect differences), bypasses JPQL's entity-aware
   validation (typos surface at runtime, not compile time), and couples the code
   to the physical schema rather than the logical object model — a column rename
   silently breaks every native query that touches it.

## Conceptual write-up

**1. Request lifecycle.** When `curl` sends `POST /users`, the request first
hits the embedded Tomcat server, which hands it to Spring's front controller,
the `DispatcherServlet`. The `DispatcherServlet` consults its `HandlerMapping`
to find that `/users` with method `POST` maps to `UserController.createUser`,
then delegates execution to a `HandlerAdapter` (specifically
`RequestMappingHandlerAdapter`), which knows how to invoke
`@RequestMapping`-style methods. That adapter resolves the method's arguments —
here, converting the JSON body into a `User` object because of `@RequestBody` —
and finally invokes `createUser`, which calls into `UserService` and returns the
saved user, which the `DispatcherServlet` then serializes back to JSON for the
response.

**2. Serialisation.** Jackson (`MappingJackson2HttpMessageConverter`), wired in
automatically by Spring Boot's auto-configuration, converts the incoming JSON
body into a `User` object — it reads the JSON keys and matches them against the
`User` class's fields/setters. If the JSON key were `upi_id` instead of
`upiId`, Jackson would not find a matching property (it matches by exact field
name by default, with no case/separator translation), so `upiId` on the
resulting `User` object would simply stay `null` — no error is thrown, the
field is just silently left unset.

**3. Spring Boot features.** The three are the embedded server, auto-configuration,
and production-ready defaults. In PayFlow: the embedded Tomcat means
`java -jar payflow-api-0.0.1-SNAPSHOT.jar` is a complete, runnable server with no
external container; auto-configuration is what turns the `h2` and
`spring-boot-starter-data-jpa` dependencies into a working `DataSource`,
`EntityManagerFactory`, and repository beans with zero manual bean definitions;
production-ready defaults show up in things like the one-line
`spring.jpa.show-sql=true` toggle and the ready-to-use `/h2-console` endpoint,
both of which are sensible conventions Spring Boot already ships rather than
things built from scratch.

**4. Spring vs. Spring Boot.** With plain Spring, this project would need manual
configuration of a `DataSource` bean, a `LocalContainerEntityManagerFactoryBean`,
a `PlatformTransactionManager`, Jackson message converters registered with
`WebMvcConfigurer`, and a servlet container (Tomcat/Jetty) set up and deployed
as a WAR — typically dozens of lines of Java or XML config before any business
code runs. Spring Boot's auto-configuration detects the dependencies on the
classpath (H2, Spring Data JPA, Spring MVC) and wires all of that automatically,
so the project only needed the four `@Entity`/`@Repository`/`@Service`/
`@RestController` layers plus `application.properties`.

**5. Stateless REST.** Stateless means each HTTP request carries all the
information the server needs to process it; the server does not keep any
per-client session data between requests. `POST /transactions` doesn't rely on
anything remembered from a prior call — every field it needs (`senderUpiId`,
`receiverUpiId`, `amount`, `note`) arrives in that one request. This matters
once PayFlow runs on three servers behind a load balancer because the load
balancer can route any request to any server without needing "sticky sessions"
— if state were kept in one server's memory, a request landing on a different
server wouldn't have access to it, breaking the client's flow.

**6. Persistence.** If transactions were stored in a Java `List` instead of the
H2 database, that list would live only in the JVM's heap memory for as long as
the process runs. Restarting the server (a deploy, a crash, a routine restart)
would wipe the list completely, losing every transaction ever recorded. For a
payments app this is unacceptable because transaction records are the system's
source of truth for who paid whom, how much, and when — losing them means
losing the ability to reconcile balances, resolve disputes, or prove a transfer
happened at all.
